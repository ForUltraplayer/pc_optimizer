- 작성: 2026-09-27, Codex. 상태: **계획 작성 완료, 구현 미착수**.
- 기준: 로컬 `master` = `32ab51f`(검증된 SP4 fast-forward 병합), 작업 브랜치 `codex/sp1-actions`. 원격 게시 없음.
- 범위: 승인된 [2차 스펙](../specs/2026-09-27-improvement-phase2-design.md) §0~2의 A1·A2·B·C·D·F1·F2. SP2/3/5, 묶음 실행, 드라이버 설치, LLM은 별도 단계.
- 먼저 읽기: [공유 리뷰 원장](../../reviews/REVIEW_LEDGER.md), [SP4 독립 재검증](../../reviews/2026-09-27-sp4-final-revalidation.md), [SP4 최종 리뷰 이월](../sdd-final-review-2026-09-27-sp4.md).
- 진행 방식(2026-09-27 사용자 최신 지시 반영): 아래 작업을 의존 순서대로 구현→해당 경계 자체 검증→원장 기록한다. 사용자가 “독립리뷰없이 진행한다”고 명시했으므로 독립 재검증을 진행/완료 조건으로 요구하지 않는다. 기존 독립 검증 이력은 보존하고 자체 검증을 독립 승인으로 표시하지 않는다. 새 에이전트 생성이나 자동 지속 감시는 요구하지 않는다.

## 완료했을 때의 사용자 흐름

추천 조치나 사용자가 고른 정리·설정 항목에서 [미리보기] → 대상·효과·주의 확인 → [실행] → 실제 결과 → 가능한 항목은 [되돌리기]. 새 프로세스·도구를 자동 설치하지 않는다. 작업이 아직 끝나지 않았으면 화면 이동 후에도 다음 변경을 막고 이유를 표시한다.

시작 프로그램은 개수만으로 개선 후보를 만들지 않는다. 사용자가 개별 항목을 선택하는 관리 흐름은 진단 Verdict를 바꾸지 않고 동일한 Planner로 들어간다. 스펙 §1의 Candidate 카드 흐름과 별도로 이 진입을 구현·문서화한다. 커뮤니티 규칙이나 관측 크기만으로 삭제 실행 버튼을 만들지 않는다.

## 공통 계약과 기존 코드 재사용

| 영역 | 기존 기반 | 추가 책임 |
|---|---|---|
| Core | Finding, FindingAction, SafetyLevel, 순수 규칙 | `Actions/`의 형식화된 조치·계획·결과·실행 범위·진행 상태 계약 |
| Probes | `Actions/CacheCleanupService`, SystemCacheToolBackend, CachePathInspector | 공통 실행 조율·파일 삭제·설정 변경·복구 어댑터. 기존 공식 도구 backend 유지 |
| App | MainViewModel, PcSpecViewModel, CacheToolsViewModel, 결과 View | 공통 확인/진행/결과/되돌리기 UI와 실행 가능 상태 연결 |
| Storage | 보호 정책, Known Folder, 다른 사용자·링크·부분 집계 검사 | 조회와 변경을 구분한 삭제 전용 대상 검증. 조회 예산 초과를 삭제 허가로 바꾸지 않음 |
| Tests | FakeClock, TimeProvider 대역, 프로브·플랫폼 대역, 소유 TestDirectory | 실패·취소·변경·늦은 종료·복구를 포함하는 경계 테스트 |

- 기존 4개 프로젝트와 .NET 10/WPF를 유지한다. Core에 Windows 타입이나 I/O를 넣지 않는다. 기존 SDD 공통 제약 문서의 ‘조회 전용’과 옛 테스트 필터는 이번 승인 스펙/계획으로 대체한다. 헤더·한글 XML 주석·리소스·익명 로그 규칙은 유지한다.
- 모델: `ActionDefinition`(Id, 범주, Scope, Safety, BatchEligible, RollbackKind, 설명/영향), `ActionPlan`(세션·SID·ScanId·만료·형식화된 대상·지문·예상치), `ActionResult`(Started, Code, 관측, 건너뜀, 복구 상태). arbitrary command/string payload 실행 금지.
- 계획은 내부 저장소가 발급하며 UI에는 ID/미리보기만 전달한다. 실행은 plan ID로 한 번만 가능하다. UTC 표시는 유지하되 5분 만료는 단조 시계로 확인한다. 다른 세션·다른 SID·잘못된 ActionId 계획은 거절한다.
- 관측·준비·실행·되돌리기가 같은 `OperationCoordinator`를 사용한다. Scan/PcSpec/Action/Restore를 실제 Task 수명까지 직렬화한다. 대기 타임아웃을 작업 종료로 취급하지 않는다. 만료 대기열 대신 Busy로 즉시 거절한다.
- SystemOnly: A1·F1·F2·HKCU 시작 항목은 거절. C는 현재 사용자 전원 API, D는 사용자 프로필 저장/대화형 화면이므로 역시 거절한다. A2만 검증된 시스템 대상 경로로 허용한다. HKLM 시작 항목은 별도 시스템 범위로 판정하되 현재 전체 시작 프로브가 User인 상태를 우회하지 않고 범위별 조회를 분리한 뒤 제공한다.
- 실행 직전 범위·권한·정책·현재 대상 재검증은 UI와 독립적으로 수행한다. 설정 저장 실패·실행 미시작·부분 변경·후속 관측 실패·복구 실패를 서로 구분한다. 서비스 정지나 임시 화면 변경도 이미 시스템을 변경한 상태이므로 Started=true다.
- 실제 삭제 테스트는 소유 fixture만. 서비스/전원/주사율/시작 설정 변경은 대역으로 기본 테스트하며 실제 적용은 별도 평가 PC에서 확인한다. 이 PC의 실제 설정을 자동 테스트 대상으로 사용하지 않는다.

## 검증 명령과 체크포인트

기준 SP4: Release 0/0, 기본 1279/1279, Smoke 22/22, ToolSmoke 1/1, 독립 재현 4/4. 이 수치를 SP1 검증 결과로 재사용하지 않는다.

& 'C:\Program Files\dotnet\dotnet.exe' build PcOptimizer.sln -c Release --no-restore

T1 이전에는 솔루션 locked restore의 RID 그래프 불일치가 알려져 있다. 이미 검증한 우회는 App csproj를 `-r win-x64 --locked-mode`로 복원하는 것이며, T1 이후에는 문서화한 단일 복원 명령으로 모든 그래프가 통과해야 한다. 실제 변경 테스트는 기본/조회 Smoke와 분리된 명시적 평가 환경으로 실행한다.

## 계획 작성 시 확인한 공식 자료

- [PowerSetActiveScheme](https://learn.microsoft.com/en-us/windows/win32/api/powersetting/nf-powersetting-powersetactivescheme): 현재 사용자 전원 계획. C의 Full 범위 제한 근거.
- [ChangeDisplaySettingsExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-changedisplaysettingsexw): 모드 시험/동적 변경/사용자 프로필 저장 플래그를 구분. D의 시험 후 유지 흐름 근거.
- [Stopping a Service](https://learn.microsoft.com/en-us/windows/win32/services/stopping-a-service): 정지 요청과 실제 상태 관측, 종속 서비스 제약. A2는 종속 서비스 범위를 자동 확장하지 않음.
- [GetShellWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getshellwindow): 셸 없을 때 NULL. 사전 확인만으로 비승격 전달 보장을 대신하지 않음.
- [Delete-DeliveryOptimizationCache](https://learn.microsoft.com/en-us/powershell/module/deliveryoptimization/delete-deliveryoptimizationcache?view=windowsserver2025-ps): FileId/IncludePinnedFiles 매개변수는 있으나 본문은 미완성. 자동 삭제 의미를 문서 제목만으로 확정하지 않음.
- [Windows 시작 앱 관리](https://support.microsoft.com/en-gb/windows/experience/startup-boot/configure-startup-applications-in-windows?nochrome=true): 사용자 설정 UI/시작 위치 참고. StartupApproved blob 쓰기 형식의 공식 보증 근거로 사용하지 않음.
